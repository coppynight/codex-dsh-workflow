# 按用户正在做的事选择执行路径

先判断用户是否正在等待这个结果、任务能否独立验收、验证环境是否已知。不要把所有开发请求固定变成「规划 → 外部实现 → 新模型审查」三段流水线。

| 工作情境 | 默认选择 | 需要避免 |
|---|---|---|
| 用户正在交互、当前结果阻塞下一步 | 最快的可靠路径；通常由当前 Codex 完成短任务 | 为很小的账面节省增加多轮等待和依赖 |
| 有一批低耦合、可独立验收的明确工作 | 先写可复用任务族契约，再按已有并发/预算能力安排隔离执行 | 把任务数量、草稿数量当成合格交付数量 |
| 复杂故障或方案尚不确定 | Astra 决定要验证的问题；按需委派独立反例、测试或定位探索 | 让多个模型自由评论，却没有可复现的新证据 |
| 依赖不可用、恢复成本超过任务价值 | 保留任务身份，安全转原生路径 | 为保留 DSH 不断扩张排查范围 |

批量交付是产品探索方向；当前 skill 没有整批费用硬限制、持久队列或关机后自动唤醒能力。实际工具不支持的调度不能只靠文字承诺；使用者未请求定时任务时不自行创建。原生 Codex 的低价执行者也应纳入选择，DSH 是可替换执行通道。

## 契约里明确验证与停止边界

任务包列出哪些自测命令由执行者运行、哪些集成检查由主控执行、自测临时目录范围，以及合理的截止/升级条件。已知运行环境能完成的验证优先复用，不为每次任务重建一套临时测试工具。已完成规定验证后，不无限扩展自测；不可因此跳过真实缺陷或遗漏最终独立验收。

权限或环境错误出现后停止受阻路径，保留证据并由环境负责人运行对应检查。不要把「不用用户干预」理解成执行者必须单独解决所有环境问题。已配置的推理强度只按实际任务风险显式调整，不因一次最快样本就把所有任务降到 low，也不为每个例行执行强制 high。

技术审查发现应给出定位、违反的需求以及最小复现或可核验依据。能运行的指控先在隔离环境验证；复现否定误报时记录裁定，不启动无意义重写。无法运行的设计/风险判断明确说明证据限制。冻结验收与事后诊断分开保存，不能事后改评分掩盖缺陷。

最终交付按「可交付产物、阻塞项、未完成/降级项」提供简明清单。实际用户请求与模型间自动协调分开记账，缺失主控消耗不能当作零。不要把后台等待直接折算成人工时间，也不要把用户仍在盯进度的等待假定为免费。
