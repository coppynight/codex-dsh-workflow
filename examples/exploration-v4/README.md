# 开放探索：工作流应在哪件事上创造明显价值？

2026-09-08。当前判断：**最值得验证的是「有预算、有验收标准的后台批量交付」——Astra 负责目标、取舍和验收，把一批可独立完成的工作变成可合并成果。** 这是下一阶段的产品假设，尚未测得批量吞吐优势。当前固定串行替换只是可选执行方式，不应继续充当产品中心。

## 先拆开那 4.5 倍耗时

v3 的 DSH 执行 514.876 秒，首个工具动作在第 95.026 秒，最后一份源文件写入在第 108.496 秒，之后还有 406.380 秒才结束。20 次工具调用中有 17 次 PowerShell 调用，包含额外自测、修正自编断言和排查输出捕获。代码写完不等于已验收，不能把后半程都算成可直接删掉的浪费；但不能把 515 秒都解释为低价模型实现速度。

因此冻结了三个消融条件，在独立目录使用真实 DSH 并发运行：保持原契约只降低推理强度、保持 high 但限制自测为已有命令、两者同时改变。规格、共享 Astra 计划和最终 17 项测试相同。低/高强度从 Host 实际 model/selection 事件核对，未更改用户全局模型设置。[协议](PROTOCOL.md)、[用量与源码](results/)。

这是单任务、每种配置一次；新三组共享服务并发，历史对照不同时运行。费用为相同高峰价格重估，包含各组初次 Astra 验收，但不包含父级协调/争议裁定及不可得的辅助标题用量。数据支持继续探索，不能证明某个参数稳定导致某个百分比改善。最便宜、最快的那组没有满足全部要求，不能摘取它宣称“更便宜又更快”。

## 比省钱更有用的发现：必须验证审查本身

三次独立 Astra 审查都指控 JavaScript 正则 `$` 接受末尾换行；在这三份源码上实际运行 `a\n`、`a\r` 等输入，均正确拒绝。三次指控都是同一误报，不能当成三个不同类型误报的统计结论。

最快组还有两个真实问题：独占创建临时文件失败时可能删除未拥有的文件；错误信息直接输出带敏感标记的路径。独立诊断实际注入一次 EEXIST，并检查无关文件是否保留，同时以无真实秘密的路径标记验证错误输出。最快组两项均失败；其余四份原始源码均通过对应检查。所有原始实现不变；诊断在审查后新增，单列为事后证据，没有改写冻结的 17 项评分。[诊断程序](diagnostic.mjs)。诊断开发中修正了 Windows `--import` URL 和文件名假设，最终版本核实钩子确实运行，并拦截实际的独占打开路径。

这说明「测试通过」和「强模型审查通过」都不能单独充当完整交付证明。**工作流应该让每个阻塞结论带可复现依据，再决定修复、接管或忽略误报。** 不应让两个模型互相评价几轮后，把真假问题一起交给用户。

## 方向排序与反对理由

| 优先级 | 产品方向 | 具体用户价值 | 最强反对理由 |
|---|---|---|---|
| 1 | 同类 backlog 的后台批量交付 | 用户继续与 Astra 推进核心工作，一批维护改动在预算和截止条件下变为可验收成果 | 原生低价子代理也可能做到；过于机械的任务用 codemod 更好 |
| 2 | 低成本并行寻找反例、测试和故障定位证据 | 让 Astra 以较低预算探索多个可能失败的方向，只读已复现的新发现 | 廉价模型可能生成错误断言；筛选负担可能超过新增发现 |
| 3 | 已有外部执行者用户的恢复与交接 | 不再手工找原任务、重复解释或冒险双写 | 很多恢复需求来自工作流自己新增的依赖，不一定胜过原生路径 |
| 4 | 普遍替换单次 Astra 实现 | 保持相同交付前提下降低模型支出 | 对当前等待的用户，串行延迟和依赖成本可能超过节省 |

原生 Codex 已具备[并行子代理及不同模型配置](https://learn.chatgpt.com/docs/agent-configuration/subagents)、[worktree](https://learn.chatgpt.com/docs/environments/git-worktrees)和[会话恢复](https://learn.chatgpt.com/docs/codex/cli)。这些不能算 skill 独有卖点。下一轮必须纳入 Astra 主控 + 较便宜原生模型，以及原始 DSH 工具不加载 skill 的对照。**若原生路径更优，DSH 应成为可替换适配器，而不是必须保留的产品身份。**

通用工作流经验也支持按任务选择复杂度、在确有独立子任务时并行，而非固定串行叠加模型。[Anthropic 工程说明](https://www.anthropic.com/engineering/building-effective-agents)。DSH 当前明确提供 low/high/max，low 适合时延敏感任务，但不能由标签推断质量合格。[DeepSeek 推理强度说明](https://api-docs.deepseek.com/guides/thinking_mode/)。

## 最值得做的下一件产品实验

选两类真实积压任务，各三件，共六件。例如多个适配器补齐取消/超时行为，或对一组已复现问题补修复与回归证据。由 Astra 写一份可复用的任务族契约，用户只交代整批目标、预算与截止时间；每件任务有独立工作区和可执行验收，结束后给出一份可合并清单和真正需要判断的异常。

三臂采用相同可用模型、工具权限、预算、并发上限、截止时间与验证标准：原生最佳配置、原始 DSH 接入、skill 策略。共享规划也同等提供给基线，失败/修复和主控筛选都记账。少一件通过就少一件产出；更多候选、更多测试或更少 token 都不能代替合格交付数。

建议预登记值得继续的门槛：同样截止时间内交付数量和质量不下降，全过程模型成本至少降低 25%；或成本相近时，用户实际操作时间减少至少 50%。这两个数字是产品继续投入的目标，不是已经测得的结果。若两项均不成立，停止包装这个方向；若原生低价执行持平或更好，优先删掉 DSH 依赖。六件任务只适合早期否证，不足以宣传普适提升。

人工时间门槛要求基线存在实际人工工作；若基线也是零，应报告没有可测下降，不能通过这个目标。三组 v4 初次 Astra 均判 repair，事后裁定成本没有计量，因此表中是模型阶段成本，不是完整最终交付成本。

当前已有任务身份、目录隔离、精简观察与恢复机制。整批预算硬限制、持久批量队列、按任务族自动验收和完整主控计量尚未实现。关闭应用后继续调度也不是当前 skill 自带能力；真实后台/定时服务需要明确配置与授权。避免把这个候选方向包装成现成无人值守产品。

公开记录可以离线重放：`node examples/exploration-v4/verify-published.mjs`。它核对冻结输入、费用账本、三份实现的 17 项测试，以及后续诊断，不调用模型。

## 对当前 skill 的调整

保留原生交互路径：用户正在等一个结果时，按预计完整时延选最快可靠执行者。外部委派只用于有明确边界、能复用验证环境的工作；环境问题停止后由主控跑已知检查，不继续生成探测脚本。后台候选任务从低耦合、可独立验收的一批维护工作开始。审查发现必须有定位与可验证依据，复现否定误报时不触发无谓重写。

**下一版最值得追求的体验是：你与 Astra 继续想产品，工作流把一批明确的工作做完，并拿着验证证据回来。** 价值尺度是额外完成多少原本积压的工作、用户少花多少注意力；成本和时延是约束条件。这一方向比“让一次 Astra 实现便宜一点”更有潜力，但仍需以上对照证明。
