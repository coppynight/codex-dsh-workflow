# 原生工具与工作流：重新审视比较基线

2026-09-08。使用者明确要求：不预设省 token 或其它优势，先观察差异，再判断是否有助于“放开用 Astra”。本文是现有证据和能力边界的核查，**不是新一轮端到端 A/B 的结果**。

## 先纠正旧实验的适用范围

此前两例实际比较的是“无工具 Astra 代码生成”与“DSH 实现后，无工具 Astra 审查并返回完整代码”。这是因本机子 CLI 执行被策略拒绝而修订的受控实验。它没有让原生 Codex 自由使用搜索、编辑、测试、原生子代理和恢复功能，也排除了父级主控开销。

因此 +9.46% 只能描述那四个受控子会话，不能推断真实工具工作流的总体效率。DSH 的 11/12 经审查到 12/12，证明该次审查修正了 DSH 结果；直接 Astra 同样 12/12，没有证明工作流总体质量更好。三项回归证明本接入层的具体保护有效；它们不证明不引入 DSH 的原生路径更容易失败。85.15% 是精简本 bridge 响应的合成字节收益，不是对原生 Codex 的省量收益。

## 已核查的差异

| 比较项 | 原生工具已有能力 / 基线注意事项 | 本工作流的具体增量 | 目前能得出的结论 |
|---|---|---|---|
| 任务拆解、独立上下文、审查、续作 | Codex 官方提供 subagents、review 和 resume；基线应允许使用 | 为 DSH、可选 Claude 规定任务与交付契约 | 不能把原生能力计作 skill 独有优势 |
| 跨工具任务追踪 | 直接 DSH API 本身有 sessionId/requestId、事件与队列；不能假设原生工具无状态或不幂等 | 持久 taskId/operationId 与内容哈希对应，连接丢失后查原任务；同一 bridge 状态可被 MCP/CLI 共用 | 增加了主控可复用的追踪机制；未测得减少多少人工干预 |
| 写入者交接 | 原生 Codex 有工作目录与权限控制；单工具路径不需要跨 DSH 交接 | cooperative workspace claim、父子目录冲突检查、turn/queue/jobs 空闲确认 | 对通过 bridge 的协作增加保护；不约束任意外部写入者 |
| 依赖不可用 | 仅原生 Codex 路径无需 DSH Host 或 DSH key | 诊断、一次有界启动、认证刷新、冷却与隔离接管 | 既降低多工具操作的出错空间，也承担自己新增依赖的维护成本；净收益未验证 |
| 主控上下文 | 原生子代理也能分离上下文、返回结果 | DSH 在自身会话实现与自测，bridge 返回摘要与证据 | 大任务可能减少主控阅读细节，属于待测假设；原生子代理是必要对照 |
| 实际可持续使用成本 | token 输入、缓存输入、输出的计费权重不同；额度还受任务与运行配置影响 | 可调整由谁执行，但 skill 不增加账号额度或改变计费规则 | 用量减少、费用减少、单位额度交付增加是不同结论 |

本次最值得进一步检验的能力是：**Astra 能否在用户较少介入的情况下，可靠地调度、观察并接管跨工具工作。** 它是候选优势，不是“最大优势已经证实”。如果用户只需要原生 Codex 就能完成任务，引入 DSH 可能没有净收益。

## 怎样检验“放开用 Astra”

不先把它压成单一分数，也不预设 DSH 必须参与。先分别记录：

- 验收通过的完整交付数、遗留缺陷与返工；
- 使用者被要求决策、手工救场、重新解释任务的次数及实际时间；
- 完整交付耗时、Astra 参与的所有阶段用量、其它模型用量与实际可取得的费用/额度；
- 正常执行与中断恢复时的续作结果、重复写入和错误接管；
- 初始化与维护依赖的额外工作。

后续有效比较至少需要三条路径：A 原生 Codex/Astra（允许正常工具、原生子代理、审查和恢复）；B 相同原始工具可用但不加载本 skill；C 加载本 skill、按需选工具。B/C 用于区分工具组合与 skill 自身的增量，A/C 用于判断用户是否值得增加这些依赖。模型访问资格与 Claude 网络门槛各组保持一致，不能把权限障碍制造成某一组劣势。

任务覆盖小改动、跨文件集成、正常长任务和预先登记的恢复场景；成功标准、预算、时间窗口和失败处理提前一致。多次交错运行并保留失败；把初始化成本单列或摊销时说明口径。费用/额度数据若受账号其它任务影响则标为不可归因，不用前后差伪造精确结果。禁止用永久禁用原生能力的弱基线证明优势。

判定规则：若相同资源下交付更多，或交付相近但显著减少用户救场，才支持相应维度的“更能放开用”。如果这些差异都不存在，就应缩减工作流，允许直接使用原生 Astra；不为保留工作流寻找新宣传口径。
