安装工作流 看成本与干预实测

01 · 原理

让每个任务，停在它该在的角色上。

Astra 的价值在想清楚：难点推理、方案取舍、验收标准的制定与最终签字。DSH 的价值在做干净：拿到边界明确、验收可判的实现任务，自测、留证、把结果交回，而不是把难题也揽下来。

这个工作流只有一条主线：难点与验收留在 Astra，有边界的实现委托给 DSH，每一轮交付都回到 Astra 验收。验收不过就定位问题、定向修复；依赖失效时保存进度，交回 Codex 继续。

⚖ 把收益做成可验证的工程目标

  • 把昂贵的判断，用在值得的地方。规划与验收留在 Astra，可执行的工作交给更低价的模型。总 token 可以更多，关键是同质量交付的成本更低、用户更少介入。
  • 数据公开，负结果也保留。下面展示局部配对用量、验收结果与故障重建；整体端到端节省和交付率仍需更多真实项目验证。
  • 可复现、可核对：样本、方法与原始用量摘录都保存在公开仓库。

02 · 分工

谁在想，谁在做，谁对环境负责。

思考与验收 · 主模型

Astra

  • 理解需求，拆解难点，给出方案取舍
  • 为每个任务写下可判定的验收标准
  • 对照标准执行最终验收；不过关就退回
  • 对外决策与无法委托的判断留在 Astra

小任务直接完成；只将值得委派的实现交给 DSH，保留自己的验收职责。

执行 · 委托实现

DSH

  • 只接受边界清晰、验收标准明确的实现任务
  • 先读现状、留快照，再写改动，产出 patch 与证据
  • 在自身权限内自测并如实报告结果
  • 验收不过时，带着失败原因迭代，持续失败时转 Codex

不自定验收标准、不替 Astra 决策、不对外发布或承诺。

环境负责人

Codex 通道

  • 拥有环境与集成测试：真机、真实环境、端到端
  • DSH 不可用（如缺少 key）时作为回退执行通道
  • 检查改动、运行集成验收，并在授权范围内合入与发布

集成测试以环境负责人的真实执行为准，不替代实现者的自测。

留在 Astra

  • 需求理解与难点推理
  • 方案取舍与风险判断
  • 验收标准与最终验收
  • 任何对外表述与承诺

交给 DSH

  • 规格明确下的实现与重构
  • 有复现步骤的缺陷修复
  • 脚本、静态页面等单一交付物
  • 可快照、可回滚的环境内改动

03 · 护栏

这些是硬约束，不是建议。

任何一条被违反，任务停下、回到负责人手里重新走。护栏本身随仓库配置一起维护。

  1. Claude：使用者确认当前网络环境

    稳定境外 IP、地区与账号符合要求，使用者明确确认后才调用 Claude。否、不确定或未回答就用 Codex 审查，继续工作。网络变化后重新确认。

  2. 缺少 DSH key → 回退 Codex 通道

    DSH 不可用（缺少 key 或配置不完整）时，任务自动回到 Codex 既有流程执行同一边界内的任务；绝不静默降级、绕过护栏或伪造“已执行”的结果。

  3. 单写者：不重复写入

    同一文件同一时间只有一个写者；写入前必须先读取当前现状。任务之间不并行写同一路径，避免双写互相覆盖、丢失对方成果。

  4. 快照与真实测试

    环境改动前留快照、留证据；静态自测在权限内完成。集成与端到端测试由环境负责人在真实环境执行——“看起来能跑”不构成通过。

人工介入：把能处理的问题留给工作流

正常任务的新增人工请求按实际记录计数。另有六项离线故障夹具验证自动恢复或安全停止：后台未启动、认证过期、未知端口占用、进程未就绪、缺 key 和 checkpoint 保留。六项通过不等于六次免人工，也不代表人工减少率。

已有授权内，Codex 负责调度、查原任务、复验、修复与降级；用户负责不可代替的需求判断、凭据和真实权限审批。查看执行规则。

怎样才可能达到 5 倍、10 倍容量？

下面是条件推演，不是实测。假设质量相同，把某一比例的 Astra 工作完全交给便宜模型，同时加入协调与返工开销。计算的是 Astra 资源容量，不含 DSH 费用、限速和时间瓶颈。

5× / 10× / 20×，分别要求每次合格交付的 Astra 净消耗下降 80% / 90% / 95%。规划与验收不能被省略；它们构成容量上限。

截至 2026-09-08，官方套餐为 Plus $20、Pro $100（5 倍用量）和 $200（20 倍用量）。本项目尚未证明“$20 媲美 $100/$200”或“一个账号顶十个账号”；月支出还应加上 DeepSeek。

05 · 安装

三步接上工作流。

需要 Codex 和 Node.js 24+。Windows、macOS、Linux 使用同一套安装脚本；DSH 与 Claude 都可按需接入。

  1. 克隆仓库

    git clone https://github.com/coppynight/codex-dsh-workflow codex-dsh-workflow

    公开仓库包含 skill、可移植接入层、测试和实测案例。

  2. 安装到 Codex 的 skills 目录

    cd codex-dsh-workflow
node scripts/install.mjs

    安装器会报告目标目录。已有安装需显式使用 --update，并保留备份。

  3. 开始使用，再按需接入 DSH

    重载 Codex，使用 $codex-dsh-workflow 描述任务。接入 DSH 时，在安装目录运行 npm ci，然后按 设置指南配置工作目录、运行时与 key。缺依赖时由 Codex 继续。

06 · 问答

常见疑问。

答案以仓库内当前配置与数据为准；这里只描述口径与边界。

价值是省 token 吗？

价值目标是降低同质量交付的成本、减少用户调度与救场。不同模型价格不同，总 token 增多也可能更便宜。Astra 继续负责规划与验收；实现、自测和定向修复交给低价模型。旧实验让 Astra 审查时重新输出完整代码，成本更高，因此新流程已调整这一分工。

什么算「完成」？谁来判定？

验收标准由 Astra 在委托时写清楚，交付回到 Astra 对照标准验收；通过后由环境负责人合入并跑集成测试。DSH 不自定标准，也不替 Astra 签字。

token 数字应该怎么读？

数字是按模型分开的：基线与工作流两列都只统计 Astra 单侧 token（小样本配对）。它们不等于总 token、总时长或总费用——那些需要另外加总 DSH、Codex 等环节，口径边界见证据区底部的说明。

两边同时改一个文件会怎样？

bridge 会拒绝被另一 DSH 任务占用的目录及其父子目录。主 Codex 也需遵守单写者规则；独立进程或手工编辑不受这把协作锁约束。接管前必须确认原任务和后台工作空闲。

哪些任务适合交给 DSH？

边界清晰、验收可判、可快照回滚的实现任务：明确的实现与重构、有复现步骤的缺陷修复、单个脚本或静态页面。难点推理、方案取舍、验收与对外承诺留在 Astra。

什么时候才能用 Claude？

每个新会话先请使用者确认：当前是稳定境外 IP，且所在地区与账号符合 Claude Code 使用要求。否、不确定或未回答，就用 Codex 审查；网络变化后重新确认。此条件只约束 Claude，稳定 IP 也不保证免封号。

DSH 没有 key，或者后台没启动怎么办？

doctor 区分本地依赖、Host 连通与模型就绪。未配置 key 时引导到本机 DSH 设置；允许自动恢复时，确认无占用后启动一次。持续失败就保存原任务标识并转 Codex，避免重复提交。
